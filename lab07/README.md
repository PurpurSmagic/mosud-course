## Трёхзначная логика

Обычное сравнение с `NULL` даёт `UNKNOWN`. Условие отбора сохраняет строку только при `TRUE`. Поэтому `order_delivered_customer_date = NULL` возвращает ноль строк. Условие `IS NULL` находит все 2 965 заказов, у которых дата действительно отсутствует.

Если сравнить два значения `NULL` оператором `=`, результатом будет `UNKNOWN`. Выражение `NULL IS DISTINCT FROM NULL` даёт `false`, а `'SP' IS DISTINCT FROM NULL` — `true`. Для текста без пропусков этот оператор сравнивает сами значения.

## Опыт с temp_ids

Во временную таблицу помещены первый по `order_id` заказ и `NULL`. Ключи в `orders` заполнены у всех заказов.

- `NOT IN` вернул **0** заказов. Для добавленного ключа предикат ложен, для остальных сравнение с `NULL` оставляет результат неизвестным.
- `NOT EXISTS` вернул **99 440** заказов. Для них в `temp_ids` не нашлось строки с равным ключом.
- После добавления `WHERE id IS NOT NULL` в подзапрос `NOT IN` вернул те же **99 440** заказов.

## LEFT JOIN и место фильтра

Фильтр `r.review_score >= 4` в `ON` определяет, какие отзывы присоединить к заказу. Если среди отзывов подходящего нет, заказ сохраняется с пустыми полями справа. В результате **99 791** строка соединения охватывает все **99 441** заказа.

В `WHERE` оценка проверяется уже после соединения. Заказ без отзыва получает `UNKNOWN` при сравнении с 4, а заказ с одними низкими оценками не даёт ни одной строки с истинным условием. Осталось **76 120** заказов и **76 470** строк. Число строк в обоих опытах выше числа заказов, поскольку у одного заказа может быть несколько подходящих отзывов.

## Профиль качества и безопасные выражения

Мини-профиль считает долю `NULL` от всех строк соответствующей таблицы. На Olist фактическая дата доставки отсутствует у **2 965 заказов (2,98 %)**, категория — у **610 товаров (1,85 %)**, текст — у **58 247 отзывов (58,70 %)**.

`COALESCE(review_comment_message, 'Комментарий отсутствует')` подставляет подпись при выводе. Пустые строки и строки из пробельных символов подсчитаны отдельно. В Olist обнаружено 0 пустых строк и 27 отзывов, состоящих только из пробельных символов. Эти 27 строк не входят в число `NULL`.

Процент вычисляется по формуле `100.0 * missing / NULLIF(total, 0)`. При пустой таблице знаменатель становится `NULL` и процент остаётся неопределённым. В отдельном примере для 1 пропуска из 4 получается 25 %, а для 0 из 0 столбец `undefined_pct` принимает значение `true`.

Текст отзыва необязателен — покупатель может поставить только оценку. Для заказа в пути также естественно отсутствие даты вручения. Повод проверить данные возникает, когда вручение уже подтверждено статусом `delivered`, а фактической даты нет. В Olist нашлось **8 таких заказов**, один из их идентификаторов выводится рядом со статусом. Отсутствующая категория товара тоже заслуживает проверки, поскольку такой товар выпадает из отчётов по именованным категориям.

## Контрольные вопросы

**1. Почему NULL = NULL не даёт TRUE?**

`NULL` обозначает отсутствие известного значения. Обычное равенство двух неизвестных значений установить невозможно, поэтому результат — `UNKNOWN`.

**2. Как предикат в WHERE влияет на строки, созданные внешним соединением?**

`WHERE` оставляет строки, где условие истинно. У строки без совпадения справа оценка равна `NULL`, сравнение `review_score >= 4` даёт `UNKNOWN`, и заказ теряется. Чтобы сохранить такой заказ и отобрать подходящие отзывы, условие помещают в `ON`.

**3. Почему NOT EXISTS устойчивее NOT IN при возможных NULL?**

`NOT EXISTS` проверяет отсутствие строки с истинным условием совпадения. Посторонний `NULL` в подзапросе не создаёт совпадения. Для `NOT IN` необходимо установить отличие проверяемого ключа от каждого значения списка, а сравнение с неизвестным значением даёт `UNKNOWN`.
