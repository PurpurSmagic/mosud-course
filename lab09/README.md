# МОСУД Практическая работа 9

**Функциональные зависимости и нормализация. Вариант 8.**

Усачев И.А., группа ИНБО-21-23. Исходное отношение описывает состав товарных комплектов и правило, по которому определяется цена комплекта.

`bundle_flat(bundle_id, bundle_name, product_id, category_name, qty, price_rule_code, price_rule_name)`

Одна строка — один товар в одном комплекте. Ниже показано, как разложить это отношение на четыре таблицы в НФБК и восстановить исходные строки. Реализация для PostgreSQL 17 и тестовые данные находятся в [lab09.sql](lab09.sql).

## Функциональные зависимости

| Бизнес-правило варианта | Функциональная зависимость |
| --- | --- |
| Комплекту соответствуют одно название и один код правила цены | `bundle_id → bundle_name, price_rule_code` |
| Товар относится к одной категории | `product_id → category_name` |
| Код правила определяет его название | `price_rule_code → price_rule_name` |
| Количество товара задаётся для конкретного комплекта | `(bundle_id, product_id) → qty` |

Минимальное покрытие получается при разделении первой зависимости на `bundle_id → bundle_name` и `bundle_id → price_rule_code`. У остальных трёх зависимостей правая часть уже состоит из одного атрибута. Из двух зависимостей также следует `bundle_id → price_rule_name`. Уникальность названий комплектов, категорий и правил в задании не предполагается.

## Ключ через замыкание

Рассмотрим `K = {bundle_id, product_id}`.

1. Начинаем с двух атрибутов самого `K`.
2. По `bundle_id` добавляем `bundle_name` и `price_rule_code`. По найденному коду добавляем `price_rule_name`.
3. По `product_id` получаем `category_name`.
4. По паре `(bundle_id, product_id)` получаем `qty`. Теперь в замыкании все семь атрибутов.

Без `product_id` замыкание содержит только `{bundle_id, bundle_name, price_rule_code, price_rule_name}`. Без `bundle_id` остаются `{product_id, category_name}`. Значит, пара минимальна. Оба идентификатора отсутствуют в правых частях минимального покрытия, поэтому любой ключ должен содержать оба. **Единственный потенциальный ключ исходного отношения — `(bundle_id, product_id)`.**

## Частичные и транзитивные зависимости

Название комплекта и код правила зависят от части ключа `bundle_id`, а категория — от другой его части, `product_id`. Название правила также определяется одним `bundle_id`, но через промежуточный атрибут. Количество зависит от всей пары. Поэтому исходное отношение нарушает 2НФ.

Цепочка `bundle_id → price_rule_code → price_rule_name` объясняет повтор названия правила у разных комплектов. Она сохраняется даже после того, как состав вынесен в отдельную таблицу. Для перехода к 3НФ потребуется выделить справочник правил.

## Аномалии исходной таблицы

**INSERT.** Чтобы завести новое правило «Сезонная цена», пришлось бы указать комплект, товар и количество. До появления первой позиции записать правило отдельной строкой в `bundle_flat` нельзя.

**UPDATE.** Название правила `BASE` повторяется в четырёх позициях. Если переименовать его только в одной, один код начнёт определять два названия, нарушая `price_rule_code → price_rule_name`.

**DELETE.** В примере у `KIT-03` одна позиция. При её удалении из плоской таблицы одновременно исчезнут название комплекта и единственное описание правила `SEASON`, хотя само правило может понадобиться снова.

## Последовательная декомпозиция

### Первая нормальная форма

Все значения атомарны. Несколько товаров одного комплекта представлены отдельными строками, количество каждого товара записано одним числом. Составной ключ различает позиции. Это 1НФ.

### Вторая нормальная форма

| Отношение после разбиения | Ключ | Причина выделения |
| --- | --- | --- |
| `bundles_2nf(bundle_id, bundle_name, price_rule_code, price_rule_name)` | `bundle_id` | Атрибуты комплекта определяются одним `bundle_id`, в том числе название правила по транзитивности |
| `products(product_id, category_name)` | `product_id` | Категория зависит только от товара |
| `bundle_items(bundle_id, product_id, qty)` | `(bundle_id, product_id)` | Количество зависит от всей пары |

Частичные зависимости устранены. В `bundles_2nf` остаётся зависимость `price_rule_code → price_rule_name`. Один код используется разными комплектами и не является ключом этого отношения.

### Третья нормальная форма

Разбиваем `bundles_2nf` по `price_rule_code → price_rule_name`. Код остаётся в карточке комплекта как внешний ключ, название переходит в справочник.

| Итоговая таблица PostgreSQL | Содержимое | Ключи и связи |
| --- | --- | --- |
| `lab.nf_8_price_rules` | Код правила и его название | PK `price_rule_code` |
| `lab.nf_8_bundles` | Идентификатор, название комплекта, код правила | PK `bundle_id`, FK на правило |
| `lab.nf_8_products` | Идентификатор товара и его категория в примере | PK `product_id`, FK на `olist.products` |
| `lab.nf_8_bundle_items` | Идентификатор строки, комплект, товар, количество | PK `item_id`, UNIQUE `(bundle_id, product_id)`, два FK на комплект и товар, CHECK `qty > 0` |

В SQL у позиции есть технический `item_id`. Обязательные поля `bundle_id`, `product_id` и ограничение `UNIQUE` сохраняют естественный ключ. В восстановленное семиатрибутное отношение входят только атрибуты из методички.

## НФБК и сохранение зависимостей

В справочнике правил детерминант — код правила, в товарах — идентификатор товара, в комплектах — идентификатор комплекта. Каждый из них является ключом своей таблицы. В составе комплектов количество определяет пара `(bundle_id, product_id)`. В SQL эта пара и технический `item_id` — два потенциальных ключа строки. При заданных бизнес-правилах детерминант любой нетривиальной зависимости в каждой из четырёх таблиц является суперключом. **Декомпозиция достигает НФБК.**

Все исходные зависимости сохранены. Атрибуты зависимости `product_id → category_name` находятся в товарах, `price_rule_code → price_rule_name` — в правилах, зависимости от `bundle_id` до названия и кода — в комплектах, а зависимость количества от пары — в составе.

## Соединение без потерь

Разбиение можно проверить по шагам. На каждом шаге общие атрибуты двух частей должны определять одну из этих частей.

1. Выделяем товар с категорией. Общий атрибут `product_id` — ключ выделенного отношения `products`.
2. Из остатка выделяем `bundles_2nf`, оставляя состав `(bundle_id, product_id, qty)`. Общий атрибут `bundle_id` определяет все сведения в `bundles_2nf`.
3. Разделяем `bundles_2nf` на комплекты и правила. Общий `price_rule_code` — ключ справочника правил.

Поэтому обратные соединения восстанавливают исходные позиции без потерь и ложных комбинаций. В SQL это дополнительно проверено на пяти строках по всем семи столбцам. Обе разности `EXCEPT ALL` пусты, то есть совпадает и число вхождений каждой строки.

## Контрольные вопросы

**1. Что означает замыкание множества атрибутов?**

`X⁺` включает сам набор `X` и все атрибуты, которые выводятся из него последовательным применением ФЗ. Если в замыкании все атрибуты отношения, то `X` — суперключ. Если при этом нельзя убрать ни одного атрибута, это потенциальный ключ.

**2. Чем 3НФ отличается от НФБК?**

В 3НФ для каждой нетривиальной зависимости `X → A` требуется, чтобы `X` был суперключом либо `A` входил в какой-либо потенциальный ключ. В НФБК действует только первое условие. НФБК строже 3НФ.

**3. Что значит «декомпозиция без потерь»?**

Для любого исходного отношения, удовлетворяющего заданным зависимостям, естественное соединение его проекций даёт в точности исходное отношение. В этом варианте пары комплектов и товаров сохраняются в `bundle_items`, а их описания однозначно восстанавливаются по ключам.
